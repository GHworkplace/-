## 🖥️ Slide 2：立题背景与痛点分析 (Problem & Background)
* **幻灯片内容**：
  * **行业背景**：传统体育（如 NBA、F1）已全面进入“魔球理论”数据决策时代，但电竞赛前决策仍存在盲区。
  * **三大核心痛点**：
    1. **数据孤岛与人工低效**：人工整理历史胜率，耗时费力且极易遗漏时间维度上的状态波动。
    2. **BP 博弈“拍脑袋”决策**：传统的 Ban/Pick 阶段缺乏多分支假设（What-If），教练组容易陷入“我以为”的思维陷阱。
    3. **静态胜率忽视动态赛局**：仅通过历史胜率预测胜负，忽略了赛场上“经济起伏”、“连败补偿”及“士气波动”等动态雪崩效应。

* **🎙️ 演讲稿（Speaker Notes）**：
  > 首先是我们的研究背景与痛点。目前，职业俱乐部在赛前准备时，数据分析师往往使用 Excel 手动汇总数据，不仅效率低下，而且由于数据是“静态”的，无法捕捉到近期队伍状态的起伏。
  > 其次，在关键的选图 Ban/Pick 阶段，决策往往依赖教练的感性直觉，缺乏科学的博弈预测分支。
  > 最后，现有的胜率预测全都是静态的，根本无法模拟在一场比赛中，如果某一方连续经济崩溃（ECO），会对整场比赛产生怎样的链式反应。为了解决这些痛点，我设计并研发了这套集“数据分析、BP博弈、动态沙盘”于一体的闭环推演引擎。

## 🖥️ Slide 3：系统架构与技术选型 (Architecture & Tech Stack)
* **幻灯片内容**：
  * **前后端分离架构**：
    * **Backend (轻量数据层)**：`Python (FastAPI)` + `SQLite` + `SQLAlchemy`，负责高并发数据多维切片与持久化，保障离线部署和隐私安全。
    * **Frontend (重度计算层)**：`Vanilla JS (原生 JavaScript)`，不依赖复杂框架以展示扎实的基础编码能力，在前端运行高密度的博弈分支计算与沙盘蒙特卡洛模拟。
  * **核心机制**：
    * 单向数据流（Single Source of Truth 状态管理）
    * 矢量图层容错渲染（SVG 动态缩放与布局防御）
    * 异步数据拉取与时空穿梭（复合 Query Params）

* **🎙️ 演讲稿（Speaker Notes）**：
  > 作为一个面向实际工程落后的项目，我采用了前后端分离的系统架构。
  > 后端基于 FastAPI 与 SQLAlchemy，使用 SQLite 作为轻量级数据库，这非常契合电竞战队的“离线与战术保密”需求。
  > 前端为了锻炼自己扎实的 Web 开发基本功，我没有直接使用 React 或 Vue，而是用原生 ES6 JavaScript 手写了模块化的组件。整个前端共享一个单一数据源 state，实现了清晰的单向数据流。同时，由于算法和推演逻辑全部运行在浏览器端，大大降低了后端的计算压力，提升了客户端响应的即时性。

## 🖥️ Slide 5：核心算法一：基于博弈论的智能 BP 推荐引擎 (Veto Engine)
* **幻灯片内容**：
  * **Ban (禁图) 推荐得分算法**：
    * $\text{Score} = (\text{OppWinRate} \times \text{Aggression} \times 1.2) + ((100 - \text{MyWinRate}) \times (1 - \text{Aggression}) \times 1.2) + \text{H2H\_Correction}$
    * 结合教练激进指数，寻找“敌强我弱”的最优解。
  * **Pick (选图) 推荐得分算法**：
    * $\text{Score} = (\text{MyWinRate} \times 0.5) + (\text{WinRateDiff} \times 0.3) + \text{H2H\_Bonus} + (\text{FormDiff} \times 2)$
    * 兼顾自身熟练度、双方克制关系与近期状态爆发值。
  * **What-If 多分支深度推演**：
    * 前端深拷贝当前 BP 进程，自动为未发生的选图决策模拟后续所有博弈分支，预测胜率，直观呈现决策利弊。

* **🎙️ 演讲稿（Speaker Notes）**：
  > 接下来介绍系统的第一个核心模块：智能 BP 博弈引擎。在电竞比赛中，BP 阶段相当于棋局的开盘，至关重要。
  > 我设计了针对 Ban 图和 Pick 图的两套权重算法。Ban 图算法融合了教练的“激进与稳健指数”，自动在“压制对方强图”和“掩护我方弱图”之间寻找动态平衡；Pick 图算法则综合考量了双方胜率差、历史交锋补正以及队伍近期的状态加成。
  > 同时，系统支持 What-If 假设分析：如果用户没有听从 AI 推荐，强行选了一张冷门地图，引擎会立刻在后台克隆当前状态，秒级演算出对手会如何应对，并给出完整的模拟胜率，以此来验证这次策略变动是否合理。

## 🖥️ Slide 6：核心算法二：蒙特卡洛赛局沙盘模拟 (Match Sandbox)
* **幻灯片内容**：
  * **经济系统状态机 (Economy State Machine)**：
    * 模拟 CS2 真实的连败补偿机制（Loss Bonus 从 $1400 到 $3400 阶梯叠加）。
    * 基于经济富裕度决定本回合的采购倾向：`Eco`, `Force`, `Buy`, `AWP`，对应不同的装备权重（1至6）。
  * **战术克制链 (Tactical Counters)**：
    * 预定义“快攻(Rush)、慢速默认(Default)、前推(Push)、主动回防(Retake)”的克制网络，动态修正回合胜率 $\pm 10\%$ 至 $12\%$。
  * **单回合胜负决策方程**：
    * $P(\text{Win}) = f(\text{BaseRate}, \text{MapBias}, \text{WeaponDiff}, \text{TacticCounter}, \text{Morale})$
    * 回合判定保留了 $5\%$ 的爆冷下限，通过随机数掷筛，输出连贯比分推演。

* **🎙️ 演讲稿（Speaker Notes）**：
  > 第二个核心算法是系统的精髓——赛局蒙特卡洛沙盘模拟。
  > 这里，我将游戏机制抽象为了一个经济系统有限状态机。系统会精确计算选手的虚拟金钱，模拟每一局是强起枪械还是经济局，并分配购买权重。
  > 此外，我还将双方战术相克（例如快攻克制前推，回防克制快攻）作为权重修正值。
  > 每一回合的胜率由绝对能力、地图属性、武器优势差、战术克制和连胜引发的士气值加权决定。最终，引擎通过生成随机数来决定回合胜负。这比纯粹算卦式的“静态胜率预测”更加逼真、更具有战术指导意义。

## 💡 答辩高频问题预演与“满分答题模板”

### ❓ 问题 1：为什么你不用 React, Vue 或 Next.js 等主流前端框架，而是用原生 JS (Vanilla JS) 编写前端？
* **🟢 完美回答模板**：
  > “谢谢老师的提问。我选择 Vanilla JS 主要出于两个考虑：
  > 第一，**巩固底层基础**。主流框架（如 React/Vue）的虚拟 DOM 和状态绑定对大一学生来说虽然方便，但容易屏蔽掉底层的浏览器渲染机制和事件循环。我希望通过手写原生 ES6 模块、手动管理 state 状态源、手写单向数据分发逻辑，来真正弄懂 Web 组件化的实现原理。
  > 第二，**计算性能与控制力**。我们的沙盘推演涉及大量的蒙特卡洛随机掷筛和多分支深拷贝（What-If 树）。原生 JS 没有任何多余的框架包装，在执行高频的纯算法计算和 SVG 画布操作时，拥有最直接的执行效率和最小的内存开销。”

### ❓ 问题 2：你的蒙特卡洛模拟（Match Sandbox）听起来很有趣，但随机性那么大，它真的有参考价值吗？你如何保证它的可信度？
* **🟢 完美回答模板**：
  > “这正是蒙特卡洛模拟的核心魅力。我们并不是简单地做一次随机判定，而是引入了**科学的概率衰减与环境因子修正**。
  > 首先，我们的胜率不是 50% 对等，而是由双方在特定地图和阵营的‘历史胜率’作为**基础概率底座**；
  > 其次，我们引入了**状态机机制**：每一回合的胜率会根据当前的经济状态（Buy、Eco）、战术风格克制链（快攻、防守前推）以及士气滚雪球效应（连胜/连败惩罚）进行动态平移。
  > 为了确保可信度，在实际推演中，我们可以让系统后台并行跑 1000 次该局比赛，通过大数定律让最终的比分分布收敛，给出高可信度的‘预期比分区间’，而不是单次爆冷的结果。这符合数值计算中用随机模拟解决确定性问题的标准方法。”

### ❓ 问题 3：你是一个大一转专业的学生，你是如何自学并独立开发出这套前后端系统的？遇到了什么困难？
* **🟢 完美回答模板**：
  > “在开发过程中，我主要通过查阅官方文档、优秀开源项目以及利用 AI 辅助学习。
  > 遇到的最大工程困难是**前后端数据格式兼容与前端 SVG 布局塌陷问题**。
  > 比如在不同模块调用地图 Blueprint 矢量图层时，由于后端命名和前端 ID 大小写微小差异，经常导致图层无法渲染。我通过在前端编写了一个‘大小写不敏感的键值容错映射层’解决了命名不规范带来的缺陷；同时，在 CSS 样式中规定了 `min-height` 和 `min-width` 的缩放防御机制，杜绝了 Flex/Grid 布局中的图层高度塌陷问题。
  > 解决这些问题的过程，让我深刻体会到了**排查 bug 需要系统的方法论**，这也极大地锻炼了我的独立解决问题和检索文档的能力。”
